To get started with https://docs.micronaut.io/latest/guide/#cloudConfiguration[Distributed Configuration] with https://docs.oracle.com/en-us/iaas/Content/KeyManagement/Concepts/keyoverview.htm[Oracle Cloud Vault], add the following dependency to your project:

dependency:io.micronaut.oraclecloud:micronaut-oraclecloud-vault[]

Oracle Cloud Vault import is importer-first and can be declared either with a connection string or with a provider-map entry.

== Connection string import

The connection string form uses the compartment ID as the host and the Vault OCID as the path:

[configuration]
----
micronaut:
  config:
    import:
      - oraclecloud-vault://ocid1.compartment.oc1../ocid1.vault.oc1.phx..?includes=DB_.*&includes=API_.*&excludes=DB_LEGACY_PASSWORD&retry-attempts=2&retry-delay=10ms
----

This format supports:
- include and exclude filters through repeated `includes` and `excludes` query parameters
- retry configuration through `retry-attempts` and `retry-delay`
- OCI authentication options through user info and query parameters, depending on the chosen authentication strategy

== Provider-map import

The equivalent provider-map configuration is:

[configuration]
----
micronaut:
  config:
    import:
      - provider: oraclecloud-vault
        compartment-id: ocid1.compartment.oc1..
        ocid: ocid1.vault.oc1.phx..
        includes:
          - DB_.*
          - API_.*
        excludes:
          - DB_LEGACY_PASSWORD
        retry-attempts: 2
        retry-delay: 10ms
----

== OCI authentication options

Oracle Cloud Vault import supports the same OCI authentication mechanisms as the rest of the Oracle Cloud integration and the importer declaration can supply the values needed to activate them. Common approaches include:

- Config file authentication with `config-path` and `config-profile`
- Simple authentication with tenant ID, user ID, fingerprint, private key, and optional passphrase
- Instance principal with `use-instance-principal=true`
- Resource principal with `use-resource-principal=true`
- OKE workload identity with `use-oke-workload-identity=true`
- Session token authentication with `session-token`

For example, config-file based authentication with a provider-map declaration:

[configuration]
----
micronaut:
  config:
    import:
      - provider: oraclecloud-vault
        compartment-id: ocid1.compartment.oc1..
        ocid: ocid1.vault.oc1.phx..
        config-path: /home/app/.oci/config
        config-profile: ALT
----

Or simple authentication via connection string user info and query parameters:

[configuration]
----
micronaut:
  config:
    import:
      - oraclecloud-vault://tenant-user:secret@ocid1.compartment.oc1../ocid1.vault.oc1.phx..?tenant-id=ocid1.tenancy.oc1..&user-id=ocid1.user.oc1..&fingerprint=aa:bb:cc&private-key=/secrets/oci.pem
----

NOTE: Oracle Cloud Vault import in this module is startup-load only. This change does not add watch metadata, scheduled polling, or automatic refresh support.

If you create a secret with the name `SECRET_ONE` in Oracle Cloud Vault, it is available like any standard configuration variable:

[source,java]
----
@Value("${SECRET_ONE}") String secretOne;
----

You can also use `@Property`:

[source,java]
----
@Property(name = "SECRET_ONE") String secretOne;
----

Values from Vault are stored as strings, but you can still bind them into strongly typed configuration using `@ConfigurationProperties`.

So if your Oracle Cloud Vault contains secrets like:

[cols="1,1"]
|===
|Name |Value

|MY_SECRETS_ONE
|Value One

|MY_SECRETS_TWO
|value two

|MY_SECRETS_THREE
|true

|MY_SECRETS_FOUR
|42

|MY_SECRETS_FIVE
|3.16
|===

You can bind them like this:

[source,java]
----
@ConfigurationProperties("my-secrets")
public record Config(String one,
                     String two,
                     boolean three,
                     int four,
                     Double five) {
}
----

Another option is to inject Vault-backed values into other configuration entries, such as datasource passwords or API keys:

[configuration]
----
datasources:
  default:
    password: ${DB_PASSWORD}
----

Legacy bootstrap-based distributed configuration remains available for migration, but it is deprecated. The old bootstrap path requires:

[configuration]
----
micronaut:
  config-client:
    enabled: true
oci:
  vault:
    config:
      enabled: true
----

That legacy path now emits a deprecation warning and should be replaced with importer-first configuration.
